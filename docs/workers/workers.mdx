tinybvh is synchronous: one big mesh blocks the thread for a second or more. `@pmndrs/bvh/worker` runs it in a pool of
module workers.

{/* snippet: pool */}
```ts
import { buildTraceScene, SceneTrees, type MeshGeometry, type TraceSceneInstance } from '@pmndrs/bvh';
import { createBvhWorkerPool, generateCpuMeshBvh } from '@pmndrs/bvh/worker';

const pool = createBvhWorkerPool(); // up to 4 workers; inline where there is no Worker (Node)
console.log(pool.usesWorkers, pool.size);

// One mesh per worker, several meshes at once. The result is a tree in the GPU layout.
const tree = await pool.build(meshes[0], { maxLeafPrimitives: 8 });

// Any API that takes a `build` function can use the pool.
const scene = await buildTraceScene(meshes, instances, { build: (geometry) => pool.build(geometry) });

// SceneTrees makes its own pool unless you hand it one to share.
const trees = await SceneTrees.create(device, { workers: pool });

// A CPU query tree built off the main thread.
const cpuTree = await generateCpuMeshBvh(pool, meshes[0]);
```

## The pool

- **Each worker is single-threaded.** tinybvh's WebAssembly build has no threads, so the pool needs no
  `SharedArrayBuffer` and no cross-origin isolation, unlike three-mesh-bvh's `ParallelMeshBVHWorker`.
- **Parallel across meshes.** A scene of many meshes spreads over the pool. One big mesh (a merged static group, say)
  occupies one worker and leaves the rest to the others.
- **Size:** one less than the logical cores, at least 1 and at most 4 (`defaultWorkerPoolSize()`). Workers start when
  builds need them, so an idle pool costs nothing.
- **Order:** first in, first out. Ask for your biggest meshes first to finish sooner (`SceneTrees` does).
- **A worker gets a build only once it has loaded.** Each worker posts a ready message when its module has run, and
  the pool sends nothing to it before that. A worker that can't load therefore holds no input, moved or copied.
- **Without `Worker`** (Node, a host that blocks workers), or when a worker can't start or load, the pool builds on
  the calling thread, one mesh per turn, so callers see the same asynchronous behaviour. Every build still completes,
  including those with `transferInput` (`SceneTrees` moves its merged groups' geometry). `pool.inlineReason` says why
  builds run inline. `worker: 'never'` always builds inline; `'always'` throws where there is no `Worker`, and rejects
  the builds when a worker can't start or load.
- **A worker that dies while building** fails that build only; the next build starts a fresh worker.

{/* snippet: cancel */}
```ts
const pool = createBvhWorkerPool({ size: 2, transferInput: false });
const controller = new AbortController();
const pending = pool.build(meshes[0], {}, { signal: controller.signal });
controller.abort(); // rejects at once with an AbortError; a running build finishes in its worker and is dropped
await pending.catch((error: Error) => console.log(error.name));
console.log(pool.stats); // { queued, running, workers, finished }
pool.dispose(); // stops the workers; unfinished builds reject
```

### Per-build events

For a tool that shows when each mesh's build waited, ran and answered: `onBuild` on the pool reports every build
`'queued'`, `'started'` (with `inWorker`: on a worker, or inline) and `'finished'` (`outcome`: `'built'`, `'failed'` or
`'cancelled'`, with `error`), with the geometry object it was given (to tell meshes apart) and the milliseconds since it
was queued. A build cancelled before it started skips `'started'`. One request's `onStart` says only when that build is
taken. A listener that throws doesn't stop the pool; its error comes on a later turn. With `SceneTrees`, its own
[`onBuild`](/scenes/scene-trees#build-events) names the mesh handles instead.

{/* snippet: pool-events */}
```ts
const names = new Map(meshes.map((mesh, index) => [mesh, `mesh ${index}`]));
const pool = createBvhWorkerPool({
    // Every build: 'queued', 'started' (on a worker, or inline) and 'finished' (built, failed or cancelled).
    onBuild: (event) => console.log(names.get(event.geometry), event.phase, event.inWorker ? 'worker' : 'inline', event.outcome ?? '', `${event.ms.toFixed(1)} ms`),
});
// Or per build: onStart when a worker takes it.
await pool.build(meshes[0], {}, { onStart: () => console.log('mesh 0 is building') });
```

## What moves and what is copied

- **Inputs are copied** into the worker (structured clone), unless `transferInput` is set. Then the caller's arrays are
  empty afterwards; an array that views only part of its buffer (glTF accessors into one BIN buffer) is copied anyway,
  so the buffer's other arrays stay usable. `SceneTrees` has the same switch as `transferGeometry`.
- **Results are transferred**, never copied: nodes, triangles, parents and bounds arrive as `ArrayBuffer`s.
- **Each worker keeps a WebAssembly heap**, 64 MiB measured (it held the largest Sponza mesh without growing). A pool
  of 4 holds 256 MiB of CPU memory for as long as it lives. `pool.dispose()` frees it, and `idleTimeoutMs` (default
  `Infinity`; 30 s for the pool a `SceneTrees` makes for itself) ends a worker left idle that long, so an idle pool holds nothing (`pool.stats.idleEnded` counts them;
  inline, the calling thread's tinybvh instance is dropped the same way). The next build starts a fresh worker.
- **Big builds belong here.** A WebAssembly memory can grow but never shrink, and one build grows tinybvh's to about
  230 bytes per triangle (Sponza merged into one 5.7M-triangle mesh: 1,349 MiB). A worker whose build left its memory
  past `recycleAboveBytes` (default 256 MiB, `WORKER_RECYCLE_ABOVE_BYTES`; `Infinity` keeps workers) is ended once it
  has answered, and the next build starts a fresh one, so the memory goes back to the system at once.
  `pool.stats.recycled` counts them. On the main thread the builder drops its grown instance too (below), but the
  memory is only freed when the garbage collector gets to it.

## Other worker builders

- `generateCpuMeshBvh(pool, input, options)` builds a [CPU query tree](/cpu-queries/raycast) on the pool.
  In three, `GenerateMeshBvhWorker` does the same for a `BufferGeometry` ([CPU raycast in three](/three/cpu-raycast#off-the-main-thread)).
- `createMeshBvhBuilder({ worker, transferInput })` is a pool of one worker, with the pool's rules.
- `createTopLevelBuilder()` builds and checks top-level shapes in a worker. `SceneTrees`' GPU top level uses it. It
  waits for its worker to load in the same way, and works on the calling thread (reported once through `warn`) if the
  worker can't load.

## Bundlers and dev servers

The pool starts its workers with `new Worker(new URL('./x.js', import.meta.url))`. We checked the built package in a
small app with each bundler:

- **Vite and webpack 5** see that line, bundle the two worker files and ship them. Production builds need no setup.
- **esbuild** doesn't: it leaves the URL as written and ships no worker files. Everything still works, but the builds
  run on the main thread (`pool.usesWorkers` is false, `pool.inlineReason` says why). To get workers, build the two
  worker files as extra entry points, where the bundle looks for them. For a bundle served from the site's root:

```sh
esbuild src/main.js --bundle --format=esm --outdir=dist \
  trace/mesh-bvh-worker=node_modules/@pmndrs/bvh/dist/trace/mesh-bvh-worker.js \
  top-level-worker=node_modules/@pmndrs/bvh/dist/trace/top-level-worker.js
```

The bundle looks for `../trace/mesh-bvh-worker.js` and `./top-level-worker.js` relative to itself (at the site's root,
`..` stays at the root). These are file paths inside the package, so check them when you upgrade.

Vite's dev server needs two settings:

- **`optimizeDeps: { exclude: ['@pmndrs/bvh'] }`.** In dev, Vite pre-bundles installed dependencies into
  `node_modules/.vite/deps`, and a pre-bundled copy looks for its workers next to itself, where they don't exist
  (`node_modules/.vite/trace/mesh-bvh-worker.js`, a 404). Excluding the package serves it as it is. It has no
  dependencies to pre-bundle.
- **`server.fs.allow`, for a checkout linked from outside the project** (`link:` or `pnpm link`). Vite doesn't
  pre-bundle a linked package, but it serves files outside the project only when a module imports them. The workers
  are loaded by URL, not imported, so Vite refuses them (`403 Restricted: outside of Vite serving allow list`). Add the
  checkout's folder to `server.fs.allow`, next to `searchForWorkspaceRoot(process.cwd())`.

Without them, `worker: 'auto'` builds on the main thread: everything still works, but slower, and
`pool.inlineReason` (and `SceneTrees.usesWorkers`, false) shows it. Browsers give no reason for a worker that failed to
load, so the message lists these causes.

## GPU builds and workers

A GPU build runs on a device, and a device's buffers can't be shared with another device. So:

1. **On the render device** (the usual case): the trees stay on the GPU with no copy. GPU H-PLOC trees take
   milliseconds, and the CPU waits only for a few stats words.
2. **In a worker with its own `GPUDevice`:** build there, read the trees back (`readLayouts`), transfer the
   `ArrayBuffer`s to the main thread, and upload them to the render device. That costs a readback, a transfer and an
   upload, and the GPU itself is still shared, so it saves no GPU time.
3. **Everything in a worker**, rendering to an `OffscreenCanvas`: one device, no copies, and the main thread is free.

`SceneTrees` uses option 1, and tinybvh on the pool for the swaps. The vanilla `workers-gpu` example runs all three
side by side on the same meshes, against tinybvh's pool alone, and reports the time to a first usable scene and to the
best trees for each ([Examples](/examples/examples)).
