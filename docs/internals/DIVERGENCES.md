# Divergences: where our code differs from its sources, and why

Dennis's rule: ports stay faithful to their source. Any change is a measured lever, with a note on why and how to undo it. This file is the one list of every change.

How to read it:

- Each row is one difference. Columns: what differs, what the source does, what we do, why (with the measurement, if one is written down), how to get the source's behaviour back, and where it lives.
- "Reason not recorded" means no doc or comment says why. Those rows are listed again under [Open](#open).
- "Not switchable" means the source's behaviour is not available. Getting it back means changing code.
- Paths without a prefix are in this repo. **ddgi** means `~/Developer/webgpu-ddgi`, the repo this code was split out of. Its docs are cited by file and entry, not by line, because they keep moving: `NOTES` is `docs/NOTES.md`, `DECISIONS` is `docs/DECISIONS.md`, `PROGRESS` is `PROGRESS.md`.
- Numbers are as written in those docs. Hardware is the RTX 3060 Laptop unless a row says otherwise. Scenes are Sponza (5.74 M triangles, 132 meshes) unless said.
- Checked: the file was first written from the docs and code comments in this repo and in ddgi. On 2026-11-13 every "source does" cell in sections 1 to 5 was read against the sources at the pinned commits: tinybvh `c9be3103cc9693b456b0a0353927c11cac7d710f` (`tiny_bvh*.h`, `kernels/traverse_bvh2.cl`), HIPRT `0629d08568fff39f9a36bf9ee800fc7bac5bb096` (`hiprt/impl/*`), and the paper "Watertight Ray/Triangle Intersection" (JCGT 2:1, 2013; its text and Appendix A and B, cited by printed page). A "Checked:" tail in a source cell gives the source file and line at that commit. A cell with no tail was not checked, and the Open list says why (the H-PLOC paper, NexusBVH and Orochi were not read).

### 1b. `BuildHPLOC`, ported to WGSL and to a CPU twin

Ported step for step from `BVH::BuildHPLOC` (`tiny_bvh_base.h`) into `src/gpu-hploc-wgsl.ts` (GPU) and `src/hploc-cpu.ts` (CPU twin). Search radius 8 and merge threshold 16 are kept as in tinybvh.

With `mortonCodes: 'tinybvh-63'`, `tieBreak: 'tinybvh'` and `maxLeafPrimitives: 1`, the CPU twin builds exactly tinybvh's tree. A unit test checks this against tinybvh itself (`buildLayout(geometry, { builder: 'hploc', maxLeafPrimitives: 1 })`, `src/hploc-cpu.test.ts:54-55`). The GPU's SAH cost is then within 1% of tinybvh's on the `bvh-hploc` page.

## 3. Woop, Benthin and Wald: watertight ray/triangle test

"Watertight Ray/Triangle Intersection", 2013. In `src/trace/wgsl.ts` (GPU) and `src/trace/cpu-traversal.ts` (CPU port). The tracer has this test only. It stores each triangle's three corners as they are, so a corner shared by two triangles has identical bits in both.

| # | What differs | Source does | We do | Why | Get the source's behaviour back | Where |
| --- | --- | --- | --- | --- | --- | --- |
| T1 | Edge functions in a fixed corner order (the Metal fix) | The plain formulation: `U = Cx*By - Cy*Bx`, `V = Ax*Cy - Ay*Cx`, `W = Bx*Ay - By*Ax`, rounded by the compiler however it likes. Checked: paper p. 69 and Appendix A (p. 78); tinybvh's optional watertight test (`WATERTIGHT_TRITEST`, off by default, `tiny_bvh.h:177`) has the same lines (`tiny_bvh_base.h:7690`) | `bvhEdgeFunction` orders an edge's two corners (by x, then y), so both triangles sharing an edge run the same arithmetic on the same operands. The triangle that walks the edge the other way negates the result, which is exact. An edge that shears to one point is set to exactly 0 | Dawn compiles Metal in relaxed math mode, which lets the compiler fuse one product into the subtraction (an FMA). Two triangles then did not get exact negatives, and on an Apple M5 Pro 2,696 of 1M shared-edge rays (1,809 transformed) slipped through; 0 after the fix. NVIDIA and Intel were not affected. About 0.1% of rays. Cost: about 3 compares and 4 selects per edge, three edges per test; the bench was too noisy to show a cost (ddgi commit 0d1c91a; ddgi NOTES "The watertight test needs its edge functions in a fixed corner order"). It was committed in ddgi after the code was moved, and ported here in `7d62375` | Not switchable. It is one path for every backend. Revert the commit (ddgi 0d1c91a) to get the plain edge functions. The CPU port is unchanged (doubles are never fused) | `src/trace/wgsl.ts` (`bvhEdgeFunction`); from ddgi commit 0d1c91a |
| T2 | Ray shear done with per-ray row vectors | A per-ray axis permutation (`kx`, `ky`, `kz`) used as indices into the corners. Checked: paper Appendix A (p. 77), `tiny_bvh_base.h:7680-7682` | Three per-ray row vectors built once with `select()`; each corner is transformed by dot products. No runtime vector indexing. Same arithmetic: products with 0 and 1 are exact, so rounding is as before and shared corners still transform identically | Indexing a vector by a per-ray value (`a[kx]`) can push it into slow per-thread scratch memory. Sponza 61 to 101 Mrays/s on the RTX 3060 once removed; watertight cost 45% on NVIDIA against 20% on Intel before (`docs/internals/design/trace.md`, parts B and C) | Not switchable (the indexed version was replaced in T0.10 part C) | `src/trace/wgsl.ts:370-426`; `src/trace/cpu-traversal.ts:55-80` (the CPU port still names `kx, ky, kz`) |
| T3 | An edge function of exactly 0 | Source: the paper (p. 71 and Appendix A, p. 78). | T5 | Conservative ray-box test | Appendix B (p. 79-80): the paper widens the box test by rounding every operation outward (`Up`/`Dn` with `1 +- 2^-23`, an error term `eps = 5 * 2^-24` on the origin, and two extra ulps on the reciprocal direction), per ray, so any triangle the watertight test can hit lies inside a box the walk enters (section 3.3, p. 72) | One multiplication: the box exit distance times `BVH_BOX_EXIT_PADDING` = 1.0000004, the fix from Ize, "Robust BVH Ray Traversal", about 3 f32 steps. ## Intentional design choices that aren't divergences

These look like differences but have no source to differ from, or they match it.

- **The tracer's walk is ours, not a port.** One loop with one 64-entry stack for both levels. Closest-hit visits the nearer child first; any-hit visits the **farther** child first by default (1.1-2.8x faster on the bench scenes with the same answers; T1.3), or the larger child with `anyHitOrder: 'larger'` (for occlusion rays from outside or across open space; trace.md, "Any-hit child order"). On the RTX 3060 (2026-11-13), `'larger'` was 1.11-1.48x far-first on instanced trees and 0.80-0.87x on merged surface rays, the same pattern as the M5 (`WINDOWS-RUNBOOK.md`, section 7). Back-face hits count (DDGI uses them). Rays in object space are not renormalized, so `t` stays in world units. Front face is the authored side, also under mirrored transforms. See `docs/internals/design/trace.md` and `src/trace/wgsl.ts:152-160`. The cross-check against tinybvh's `traverse_bvh2.cl` is section 6.
- **The node layout** (64 bytes, two child boxes, Aila-Laine) is tinybvh's `BVH_GPU` layout, "byte for byte ours" (`docs/internals/design/bvh-framework.md`). Every builder writes it. Scenes store nodes quantized by default since 2026-11-13 (32 bytes, ours: `docs/internals/design/compressed-nodes.md`, option A), packed from that layout; `nodeFormat: 'f32'` keeps it. The triangle record is ours (W4).
- **Kept as published:** H-PLOC's merge threshold 16 and search radius 8 (tinybvh and NexusBVH use 8; 16 is "half the 32-wide wave of the paper", `src/hploc-cpu.ts:62-66`); Apetrei's index tie-break in the LBVH (HIPRT's rule); the Arvo box formula (S4).
- **The WASM is tinybvh's headers, unchanged.** Only the flags and the wrapper differ (W1-W6). The licences travel inside the `.wasm` file's TypeScript wrapper (`THIRD_PARTY.md`).
